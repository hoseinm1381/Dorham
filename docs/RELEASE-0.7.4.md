# Dorham 0.7.4 — visible screen quality and bandwidth

Quality and Bandwidth selectors now sit directly above Share screen, rather than inside connection diagnostics. The button also shows resolution, frame rate and the effective bandwidth ceiling. Available choices are 480p/720p at 15/30fps and 300, 450, 600, 750, 900, 1050, 1200, 1350 or 1500 kbps. New preferences default to 720p/15fps and 450 kbps, persist locally and apply to the next capture. Changes during sharing update the current capture and encoder without opening another picker or replacing the sharing lease.

Screen-share startup previously discarded the quality argument and always used 720p/15fps. Both browser transports now honor the selected mode at startup. A 30fps request first obtains its permitted lease setting; fallback slots stay at 15fps and promotion still requires an explicit choice to increase frame rate. The UI uses the actual requested frame rate when displaying an active fallback share. Unsupported server ceilings are shown and higher bandwidth choices are disabled.

Bandwidth is the combined video/shared-sound encoding ceiling. For example, selecting 300 kbps with shared sound allocates 252 kbps to video and 48 kbps to audio; 1500 kbps allocates 1452 and 48 kbps. Without shared sound, video can use the full selected ceiling, independently of the resolution preset. Actual traffic can be lower; transport/protocol overhead is additional. This is a cooperative encoder setting, not a network billing firewall. See the [WebRTC encoding-parameter definition](https://www.w3.org/TR/webrtc/#dom-rtcrtpencodingparameters-maxbitrate).

The pilot's screen ceiling changes from 450,000 to 1,500,000 bits/second to make the full selector usable. Other environment bytes, sharing-slot limits and frame-rate policy are preserved. Older clients retain their legacy preset behavior under the raised server ceiling; the new selector defaults to 450 kbps. No schema change, dependency, added media stream or polling loop is needed. Windows remains unsigned. Native Android forwarding/cap source is aligned, but an Android build/device test is deferred.

## Verification

Direct two-client Chrome and isolated SFU checks exercise all nine caps on actual RTCRtpSender parameters, initial quality selection, live resolution/fps changes, rewatching, persistence, cancellation and lease/capture continuity. The SFU check includes shared sound inside the selected budget. A fallback publication decodes, remains at 15fps when promoted, changes to 30fps explicitly and stops under moderator revocation. Desktop/mobile screenshots are inspected; mobile capture waits for navigation to finish opening. Synthetic capture verifies transport/settings behavior, not a physical screen picker's visual quality.

Lint, TypeScript checks, all **140 unit/API tests in 25 files**, production builds and the standalone compiled-server smoke check pass. The latter checks registration, message deduplication, seven game lobbies and schema 8. The packaged Windows app was silently installed; all 40 installed web files and four desktop-shell files match the built inputs. The installer is in `artifacts/v0.7.4/windows`.

Public Chrome and installed Windows both decode bidirectional voice and screens through forced TURN/TLS. Chrome exercises all nine bandwidth choices with shared sound; Windows exercises 300/750/1500 kbps and live frame-rate changes. Both retain a single capture while changing settings. Explicit watching, deafen, microphone gain, local voice playback, mute/unmute cues, invitation controls and revisioned permissions also pass. The first public run stopped at a microphone-gain ratio assertion with a transient baseline; waiting 1.5 seconds before taking the baseline made both directions pass the same tolerance (about 2.5× at 250%). No microphone implementation was changed. The failed log and successful measurements are retained. The browser memory guard remained below its 4 GiB budget.

The independently downloaded pre-release backup verifies 38 table digests, four file digests, SQLite integrity and foreign keys. Rollout preserves 35 persistent table digests and all three avatar/attachment files. Only `SCREEN_MAX_BITRATE` changes; all other environment bytes remain identical. Four services are active, normal-DNS HTTPS returns the exact built HTML, and the previous application remains in `/opt/dorham-before-0.7.4`. Each public test's two synthetic accounts, server and media room were removed using its ownership manifest; the final real-data counts remain 12 users, three servers and 36 messages. No server password or authentication settings were changed.

Source, compiled-server and verification archives plus SHA-256 checksums are in `artifacts/v0.7.4`; `release.json` links the final source and compiled-branch commits to the evidence. Logs and measurements use the `v074-` prefix. No new voice/screen capacity certification, physical capture/acoustic acceptance, dependency advisory audit or Android-device test is claimed.
