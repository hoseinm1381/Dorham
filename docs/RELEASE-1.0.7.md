## Channel mentions

Type `@` in a channel message to choose a server member. Search by username or display name, including Persian names; use arrow keys and Enter/Tab or click a suggestion. Escape closes the picker, Shift+Enter keeps a new line, and choosing a name does not send the message. The inserted tag is `@username`. Multiple individual tags are supported. Ordinary emails, URLs, backtick code and unknown usernames remain plain text.

Eligible tagged recipients receive the existing in-app notification banner and message sound while outside the conversation, unfocused, or viewing a dialog. Clicking the banner opens the correct server/channel. A focused open conversation highlights the tag/message without an extra sound. Do not disturb and the message/mention sound preference silence the cue. This uses the app's existing live notification system; no operating-system notification permission or push service is added. Offline users see stored tags and normal unread channel state when they return; historical sync does not generate fresh alerts.

The backend resolves tags against actual server members with channel read permission, excluding blocked users in either direction and unavailable accounts. It stores recipient identities when the message is written, so later joins cannot turn older plain text into a notification. Self-tags do not notify; repeated tags create one recipient. Repeated send requests, edits, reactions, history and reconnect synchronization do not repeat alerts. Edits update the visible stored tags silently. No role-wide or everyone ping is added.

## Additional memory safeguards

Output size and quality are retained. In the local synthetic three-upload probe, RSS growth fell from about 48 to 18 MiB, with identical output hashes; production savings remain unmeasured. ## Windows screen-sharing fix

The operator reported **Invalid capture constraints** on Windows 1.0.6. The same error was reproduced in the original local 1.0.7 package before its picker opened. Electron supplies the requesting origin as `dorham://app/`; the previous handler accepted only `dorham://app` and returned an empty capture grant. The corrected handler accepts those two exact origin spellings, requires the live trusted main frame, rechecks it before granting the selected source, and uses `null` for denial/cancellation as specified by the [Electron Session API](https://www.electronjs.org/docs/latest/api/session#sessetdisplaymediarequesthandlerhandler-opts). Foreign/lookalike origins and other frames remain denied.

Native testing also exposed repeated-share playback using an emptied browser-owned stream container in the mesh path. Video playback now holds its own stream container around the live receiver track, while signaling still uses the announced stream ID. This fixes stop/restart playback without changing microphone capture or the SFU implementation.

## Server memory cleanup

The read-only live audit found roughly 1 GiB available on the 2 GB host, and a 329 MiB speech worker kept resident after TTS. Local 1.0.7 now retires the child after 180 idle seconds, waits for exit before replacement, expires speech caches during quiet maintenance and caps cached audio at 8 MiB. Active/queued speech remains protected. Administrator metrics expose worker/cache state. Models reload on demand, so the first TTS after idle may start more slowly. On a fresh worker, current eligible listeners hear a bundled loading announcement in their own app language: English or Farsi. The recordings do not require synthesis at playback time; they queue before the message, honor TTS/deafen/volume/output settings, expire quickly and do not repeat for warm requests. Their versioned hashed URLs are precached with the PWA and bundled in Windows. See [speech behavior and asset sources](TTS.md#cold-start-announcement-local-107). See [measurements, tests and deployment limits](MEMORY-1.0.7.md). No live worker or service was stopped.

## Member controls

Right-click a member in the member list, voice participants, expanded voice cards or a message author. The menu offers the actions the server authorizes: voice disconnect, server mute/deafen, screen-share restrictions, move to another voice channel, timeout, server kick and server ban. Moves also support dragging a voice participant onto another voice channel in the same server. Destinations retain capacity, access, tag and lock checks.

Punitive actions require a higher role and the relevant moderation/member-management permission. Administrators cannot punish peer administrators; they may move each other between voice channels. Moderators may also move peer moderators. The server owner is protected from server-role moderation; existing instance-administrator authority is retained. Self-punishment is hidden. Authorization is checked again on the backend for every action.

Timeout presets are 1 minute, 10 minutes, 1 hour, 1 day and 1 week, with optional reasons and early removal. A timeout disconnects active voice and blocks messages, reactions, edits, attachments and voice joining in that server, including listen-only joins. Reading and unrelated direct messages remain available. Leaving/rejoining does not bypass it. Access resumes at expiry; maintenance refreshes clients after expired entries are removed.

Server kicks permit a later invite rejoin; server bans block it until unbanned. The server's Members settings include the ban list and permission-checked Unban action. Confirmation forms cover kick, ban and timeout. English/Persian labels, keyboard dismissal and viewport-clamped menus are included.
