# Dorham 0.4.1: voice CPU and keyboard controls

Voice refreshes previously rebuilt every room for every socket, while SFU permission reconciliation rewrote unchanged participant permissions. Heartbeats also rebuilt full member permissions repeatedly. The new path shares transaction-scoped reads, builds each room once per refresh, coalesces overlapping refreshes with a trailing pass, suppresses unchanged events, and applies SFU permission changes only when the current server grants differ. Authorization remains current on every pass; no permission result is cached across commits. Moderation still waits for confirmed SFU enforcement and fails visibly on an SFU error.

In a local, identical SQLite/Socket.IO benchmark with ten users, four leases, 100 heartbeats and ten refreshes, the old source at 787c5b7 performed 19,970 SQL reads, 800 writes and used 625 ms CPU. The optimized SFU control path performed 2,032 reads, 500 writes and used 234 ms CPU: 89.8% fewer reads and 62.6% less CPU in this measured control workload. These are local process measurements, excluding real SFU packet forwarding; they do not establish an equivalent percentage reduction in whole-VPS CPU.

Reproduce the current isolated workload with `npm exec -- tsx scripts/voice-control-benchmark.ts`. It creates temporary local accounts/database, records `artifacts/evidence/cpu-control-current-sfu.json`, and removes the fixture on exit. It needs no production credentials or external SFU and does not certify media capacity. CPU timings vary with workstation load; SQL operation counts are the more repeatable comparison.

The final-source repeat measured 2,035 reads, 500 writes, 202 ms CPU and 295.72 MiB RSS. Small read-count variation comes from time-sensitive permission/lease query parameters; no result is cached beyond its transaction.

The frontend now collects full WebRTC diagnostic statistics only while the diagnostics dialog is open. LiveKit microphone changes are serialized and deduplicated; heartbeats begin during connection setup. Initial Socket.IO connection no longer starts a second concurrent SFU join, and cancelled joins cannot resurrect a disconnected room. Muted/PTT calls prepare an already-muted microphone so the first talk press does not wait for a new capture request. Member rosters refresh when users or server roles change rather than on every voice/unread snapshot.

Adaptive screen video now attaches through LiveKit's video-track API, so the SDK can observe video visibility and dimensions. Previously the raw MediaStream attachment bypassed that requirement and could leave adaptive video paused. A screen arriving before its lease notification is attached when the authorized room snapshot arrives. Explicitly closed screens remain closed. Publishing also waits for the SDK's screen permission event, with bounded timeout/cancellation: the database lease acknowledgement can precede SFU signaling. This fixes the observed permission-denied race without weakening publication permissions.

## Voice input

Settings → Voice input & hotkeys offers Open microphone, Push to talk, and Toggle to talk. Choose a talk key with optional Ctrl/Alt/Shift modifiers. Preferences are saved on this device. Push-to-talk starts muted and closes when the held key or required modifier is released. The microphone button can lock push-to-talk muted. Toggle mode starts muted after a new call, mode change or safety release. Typing and hotkey-recording fields ignore talk presses.

The website requires page focus. Losing focus releases its talk state. The Windows application can enable “Work while using games and other apps,” including calls kept in the tray. Its small Windows helper polls only the configured key and modifier states; it does not collect text or general key history. It runs only during an enabled call, stops when the call or application ends, and releases on lock/suspend, helper exit or missing heartbeat. Startup requires a fresh key release before accepting a press. Background input in elevated/protected games and physical keyboard behavior still require user testing.

The native helper source is `apps/desktop/native/VoiceHotkey.cs`; Windows packaging compiles it using the Windows .NET Framework compiler and includes the executable outside Electron's ASAR archive. No new npm/runtime dependency or administrator permission is required. Context isolation, renderer sandboxing and the narrow preload bridge remain enabled.

## Verification and rollout

Lint, type checking, all 58 unit/API tests, and production API/web/Windows builds pass. Tests include transaction-read invalidation, single-flight trailing mutations, fair acknowledgement under continuous refresh requests and error recovery, private room snapshots, lightweight heartbeats, SFU grant differences and immediate moderation, key validation, repeat suppression, microphone safety transitions, SDK permission wait, initial connection and cancelled join handling. Browser checks exercise the actual captured microphone, saved bindings, page focus loss, real decoded mesh media, blocked ICE feedback, private inline media and layout. The installed final Windows release passes actual OS key-state injection while another isolated window has focus and while Dorham is hidden, helper process termination while unmuted, and simulated lock while unmuted. No Android build or device test is part of this update.

The first broader browser run caught a test timing race (a key was pressed before voice had joined), and the removal of background stats exposed a missing diagnostics-on-open refresh. Both were corrected; the affected hotkey, decoded-media and blocked-ICE scenarios then passed. Original failed logs are retained. Real SFU decoded-media/layout checks use an isolated local database and delete only their own UUID rooms.

The final revision also passes all nine expansion browser scenarios (including profile/role refresh), the real Iranian SFU screen-first/self-preview/departure-cue scenario, and the focused PTT/toggle test against that SFU with actual captured track state assertions. The installed unsigned Windows release was tested from `artifacts/v0.4.1/installed-release/Dorham.exe`; the installer hash is recorded in the release evidence. These small checks stayed under the normal 4 GiB browser budget.

### Heavy media result: failed acceptance

Five production batches and one isolated-control comparison exercised ten Chrome contexts with ten synthetic microphones and four moving screen captures. All five production batches' 50 temporary accounts and private servers were removed by exact manifests; five existing accounts and their server/messages were preserved, with SQLite integrity and foreign keys checked. The isolated fixture's ten accounts/database and its own UUID media rooms were also removed.

The full ten-user/four-share media gate did **not** pass, and no successful five-minute hold is claimed. Earlier production attempts hit negotiation timeouts and reconnects. The isolated control-plane comparison (local API/database, real Iranian SFU, signaling over a private SSH tunnel) retained all ten connections, received audio energy on all 90 remote audio subscriptions, and decoded up to 34 of the required 36 video subscriptions. Its final aggregate video RTP packet-loss counter was 18.84%; some individual streams were much worse. The SFU also logged congestion/loss warnings. These support network impairment as a contributor, but do not isolate every server/client/network cause or certify a production-path capacity result.

Browser memory stayed below the authorized 6 GiB. The largest measured total was 5,238.2 MiB; the final comparison stopped at its conservative 5,200 MiB owned-browser threshold after the media gate had already failed. Across these attempts the API peaked at 199.45 MiB RSS and SFU at 175.48 MiB RSS; minimum VPS available memory was about 1,292.5 MiB. Registration password hashing causes short CPU spikes; these must not be reported as steady call CPU. A final comparison sample showed SFU 52% CPU and production API 0.19% while the test used the separate local control plane. This is not evidence that the VPS supports a stable heavy call.

Next capacity diagnostic: run clients on independent devices/networks, record selected ICE transport, RTT, packet loss and per-host CPU during a verified hold, then compare direct UDP with the existing integrated TURN/TLS path. Change one variable at a time before deciding on a VPS upgrade. No paid upgrade or service activation has been made.
