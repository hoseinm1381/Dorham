# Local Farsi and English voice-channel speech

The current web/Windows 1.1.1 revision prepares one complete WAV before playback, replacing two-half delivery. A tiny percentage bar beside the message shows completed preparation work and disappears when ready. Natural sentence/language boundaries are retained; a long inference can hold the percentage until its sentence completes. The three-second minimum buffering remains. Audio/progress are private to eligible voice members. The persistent worker, memory-pressure eviction/recovery, bounded identical-text reuse and host-specific optimized graphs remain enabled. Amir, the 30% CPU cap and 1 GiB service limit are preserved. See [current release verification](RELEASE-1.1.1.md) and [retention/model policy](TTS-PERFORMANCE-2026-11-04.md).

Persian voice status (2026-11-02): restored the previous Piper Amir voice at the operator's request after Mana listening feedback. The 30% speech CPU cap and other TTS controls are preserved. See [deployment and rollback history](TTS-MANA.md).

Use `/tts your message`, or enable the TTS checkbox beside the composer. The ordinary text message is committed first, with the command removed. If its sender has no current voice membership, it remains a normal message. Otherwise speech is generated locally and delivered only to people who were in that same voice channel when it was sent and still have the same membership epoch. Being in another voice channel, viewing the same text chat, or knowing the audio URL does not grant access.

Speech uses local Piper 1.8.0 with the Persian amir medium and English LJSpeech medium voices. Mixed-script messages are split between the two voices. These models are not OS/browser voices and do not require an external speech service during use. The model cards are preserved under docs/licenses (Persian dataset CC0; English dataset public domain). Piper and the separate worker are GPL-3.0-or-later; the upstream license is preserved alongside the cards. Primary references: [Piper Python API](https://github.com/OHF-Voice/piper1-gpl/blob/main/docs/API_PYTHON.md), [Persian model](https://huggingface.co/rhasspy/piper-voices/blob/main/fa/fa_IR/amir/medium/MODEL_CARD), [English model](https://huggingface.co/rhasspy/piper-voices/blob/main/en/en_US/ljspeech/medium/MODEL_CARD).

## Cold-start announcement (local 1.0.7)

A fresh worker signals startup before the speech request is written. Eligible listeners hear a bundled recording in their own interface language: “Text to speech is loading.” or «سامانهٔ گفتار در حال آماده‌سازی است.». The WAV files are already generated and do not depend on the cold engine, browser/OS voices or an external speech service. These existing recordings remain unchanged; generated Persian message speech again uses Amir. No native rebuild was required for the server-side rollback.

The announcement and message use one playback queue and the selected output/sender volume. Leaving voice, deafen/server-deafen and Mute TTS discard or stop both. The server rechecks the sender, stored message, permissions and current membership epochs before routing a startup event. Announcements expire after 15 seconds; duplicate request IDs do not repeat them. A warm worker does not announce. A translated loading notice also appears in the app. Browsers may require a gesture before any audio can start.

Assets and hashes: `assets/tts-loading/manifest.json`. Rebuilds verify and copy the recordings; Vite hashes the WAV filenames; the player and PWA use matching version queries. The browser check verifies cached responses contain the full PCM data, avoiding empty unversioned audio cache entries observed during testing. `scripts/record-tts-loading.py` can regenerate them explicitly with the already provisioned Piper runtime and verified voice models. This asset-preparation step never runs at app startup or during a normal build. The initial clips were streamed from a short separate process using the existing server voices, with no remote files written and no service/configuration changes. Only the public loading phrases were used.

`TTS_IDLE_SECONDS=180` controls model retention when `TTS_KEEP_WARM=false`. The synthesis deadline defaults to 60 seconds, or 300 seconds when the optional TTS CPU cap is enabled. `TTS_TIMEOUT_SECONDS` can override it (1–3600 seconds). Generated message audio still expires after 120 seconds with an 8 MiB aggregate delivery/reuse cache ceiling.

## Provisioning

Run `sudo python3 deployment/install-tts.py` explicitly on the Linux host. It creates an isolated environment under /opt/dorham-tts, pins Python dependencies from tts-requirements.txt, verifies the model hashes and pinned source revision in tts-models.json, and does not change system Python. App startup never downloads a runtime or voice. DORHAM_TTS_PYTHON and DORHAM_TTS_MODELS can override the default interpreter and model directory. The service user needs read/execute access only. The separate speech worker runs with one ONNX thread at lower scheduling priority and retains the models between requests until 180 seconds of inactivity (checked during maintenance). Active or queued synthesis prevents retirement.

The first request may take longer while models load; the worker allows the configured synthesis deadline and discards output from an expired process. Speech is limited to 400 stored characters and one request per sender every four seconds; the server queues at most four jobs. Longer/rate-limited/unavailable requests remain normal chat messages with a sender notice. Synthesized audio is held only in a bounded in-memory cache for two minutes; it is authenticated, voice-epoch checked, private/no-store and never cached by the PWA. No message text is written to synthesis logs.

## Linux TTS CPU isolation

See [TTS CPU cap operations](TTS-CPU-CAP.md) and `deployment/dorham-tts-cpu.conf.example`. `TTS_CPU_PERCENT=30` limits the combined speech worker, its threads and descendant processes to 30% of all online host CPUs. Cold starts are included: Linux creates the Python process directly inside the capped cgroup, before interpreter startup or model loading. The Go API, LiveKit and proxies are outside this CPU quota. Existing service memory limits still cover the API plus its speech workers.

The cap requires Linux cgroup v2, kernel support for `CLONE_INTO_CGROUP`, and a systemd service configured with `Delegate=cpu` and `DelegateSubgroup=app` (systemd 254 or newer). If a configured cap cannot be established, speech fails closed with the existing unavailable notice; it never launches an uncapped fallback. `TTS_CPU_PERCENT=0` disables isolation for development and other platforms. Idle retirement and timeouts terminate the TTS cgroup descendants together. Slower generation under the cap is expected.

Moderator mute/speak permissions are enforced before and after synthesis. Leaving the channel before generation completes cancels delivery. Deafen/server-deafen prevents access; leaving/rejoining does not restore access to previous audio. The web player drops queued/playing speech when leaving, deafening or muting TTS. Speech uses the selected audio output and the sender's configured playback volume. Browser autoplay may require a user gesture. The matching native 1.0.4 rebuild includes this player; physical Android playback remains an operator acceptance check.

Real Farsi, English and mixed synthesis are checked separately from browser delivery. Automated routing checks use generated PCM speech fixtures and test account membership; they do not certify pronunciation or physical speakers. No new media capacity certification is implied.
