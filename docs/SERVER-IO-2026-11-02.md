# Server storage incident, 2026-11-02

The site and SSH intermittently timed out before any TTS CPU-limit deployment or load test. Initial inspection found no running speech worker. The provider dashboard reported the VM powered on, but its requested reboot did not change the guest boot ID.

A three-second process sample found the QEMU guest agent consuming 83.75% of the single vCPU, versus 0.95% for Dorham and 2.86% for LiveKit. Its normal restart stalled at SIGTERM. Terminating only that service's main process allowed its pending restart to complete, reducing its measured CPU to 0.44%. Application and proxy process identities were preserved during that recovery.

Kernel logs separately recorded storage-blocked tasks lasting more than 122 seconds, including Dorham and journald. A fresh private database/uploads/config/backend backup was created and independently verified on the operator's laptop before an explicitly authorized SSH reboot. The boot ID then changed, all services returned, and public readiness improved from a multi-second sample to 0.21 seconds. The application retained both existing 1024 MiB memory limits.

## Post-reboot disk measurement

Over 21.574 seconds, the root disk wrote 1,150,976 bytes in 119 write operations and read zero bytes. Dorham itself wrote 159,744 bytes (about 7.2 KiB/s). LiveKit, Caddy and HAProxy wrote zero disk bytes in that interval. Root-disk busy time was 31.79% despite this small throughput. Six disposable 4 KiB write-and-fsync probes, including interpreter startup, took 198, 552, 1452, 1158, 114 and 68 ms. The probes were separate from production data.

This establishes high write latency under low throughput, not massive application transfer volume. It does not identify the physical host cause. The QEMU guest-agent problem and storage delays are distinct observations; the reboot did not eliminate the latter. No filesystem, SQLite synchronous/durability setting, service I/O quota or unrelated service CPU cap was changed.

## Relation to reported UI errors

The exact voice warning comes from the client's 10-second Socket.IO acknowledgment deadline. Heartbeats run every five seconds. Long database/storage stalls can delay those acknowledgments while audio continues through the separate LiveKit process. That is a supported explanation for the incident, not proof that every historical timeout had the same cause.

The separate `Refresh your session and retry.` warning is a CSRF proof rejection. Browser tabs share a login cookie while storing their proofs independently. The client fix refreshes a rejected proof and retries once only for the same account, retaining the original mutation request ID. It refuses to replay an action after an account switch. Socket reconnects also obtain a current proof. CSRF enforcement and durable message writes are preserved.
