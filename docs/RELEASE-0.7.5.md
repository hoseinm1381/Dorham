# Dorham 0.7.5 — conversations, recovery and simpler sharing

Direct messages now show only conversations with at least one sent or received message, newest first. Choosing a person opens their composer without adding an empty chat to the list. The empty home prominently explains the + next to Direct messages; that button opens the searchable people directory. Message creation changes the order immediately on both clients, and the order survives reloads. Edits, reactions and read receipts do not bump a conversation. Closing and blocking chats keep their existing behavior and history.

Invitation creation includes a destination selector. Guests go directly to its permitted text channel after choosing their name, including when their join consumes the last use of the invitation. Older invitations, deleted destinations and inaccessible destinations fall back to the first visible text channel. Voice destinations show an explicit Join voice action; entering a link does not start microphone capture. Existing registered users joining invitations use the same landing behavior.

Registration supplies eight one-use recovery codes. The database stores their hashes; plaintext codes are displayed in memory and can be downloaded privately. New users confirm they saved them before continuing. Existing registered accounts receive a reminder once per account, across devices. Previously saved codes remain valid unless the user explicitly confirms their password and generates a replacement set. An existing hashed set cannot be redisplayed. The reminder can be deferred to Account settings → Privacy → Account recovery. A password-reset guide appears both there and on the sign-in screen. Guest conversion also offers recovery setup. Resetting with a code consumes it and revokes existing sessions. No existing passwords are changed by this upgrade.

Owners and users permitted to manage channels can upload or remove a server icon in the server overview. PNG, JPG and WebP inputs use the existing bounded client resize, server decoding, 128×128 WebP conversion and shared avatar quota. The rail refreshes immediately for other members. Members without management permission cannot change icons.

Voice clarity is an optional, default-on browser/Windows microphone effect with two native Web Audio filters: an 80 Hz high-pass to reduce rumble and a gentle +2 dB presence adjustment around 2.5 kHz. It runs on the sending device in the existing microphone graph; it adds no model download, server DSP, media stream or polling loop. Switching it off disconnects the filters. This is subtle speech filtering rather than a promise to repair every microphone or connection. The private voice test includes the same effect. See the [Web Audio filter specification](https://www.w3.org/TR/webaudio/#BiquadFilterNode).

The normal microphone-gain control remains 50–250%. An unchecked-by-default **Allow microphone boost up to +30 dB** checkbox unlocks a decibel slider up to +30 dB (about 31.6× signal amplitude). Its visible warning explains loud noise and distortion, and recommends the private test and checking with the listener. Disabling boost immediately caps the gain at 250%. Mute gating remains after the clarity filters, and gain applies to both the transmitted track and local test playback. This increases signal amplitude; it does not promise 32× perceived loudness or clean output from an already clipping microphone.

The voice sidebar now shows a Share screen button. Clicking it opens a setup dialog with these presets:

| Preset | Resolution | FPS | Maximum bandwidth |
| --- | --- | --- | --- |
| Save data | 480p | 15 | 300 kbps |
| Balanced | 720p | 15 | 750 kbps |
| High quality | 720p | 30 | 1500 kbps |

Advanced exposes separate resolution, FPS and bitrate choices (480p/720p, 15/30 FPS, and nine caps from 300 to 1500 kbps). Remembered custom settings, including the earlier 450 kbps default, remain available. Presets respect the server and sharing-slot limits. Sound selection is inside the dialog. An active share has an Adjust sharing settings button; Apply updates its current capture and lease without another screen picker. Cancel leaves voice connected and releases any reserved sharing lease. Bandwidth includes shared sound, and actual use can be lower; transport overhead is additional.

## Verification

Release checks and deployment evidence are recorded under the `v075-` prefix in `artifacts/evidence` and `artifacts/logs`. The update adds schema migration 9 with only additive columns and a message-activity index. Migration/restore checks preserve existing accounts and messages. No new runtime dependency is required. Windows remains unsigned; native Android packaging and device acceptance are deferred.

Local checks: lint and TypeScript pass; all 145 unit/API tests pass. Six new browser scenarios cover DM discovery/order, guest landing, account-level recovery reminders, sharing setup/cancellation, icons and boost preferences, and real Web Audio processing. Measurements show 31.62× graph gain at +30 dB, zero output while muted, about 0.152× amplitude at 30 Hz with clarity enabled, and about 1.26× at the presence frequency. Separate two-client Chrome voice measurement observes about 31.95× decoded amplitude from a quiet synthetic source, retains silence while muted and restores the normal range. Existing 50–250% gain, capture restart, rejoin and reload checks pass. These synthetic measurements establish signal behavior, not subjective microphone quality or physical acoustic acceptance.

Two-client screen checks pass in both direct and isolated SFU transports, covering all nine caps, resolution/FPS changes, unchanged capture and lease, rewatching, preference persistence, cancellation and mobile overflow. The SFU check includes shared audio inside the selected cap. The isolated SFU listener measures about 31.73× decoded amplitude at +30 dB, with mute silence and normal-range restoration. The seven existing application scenarios pass; the chat scenario now uses the requested + discovery flow. A randomized poker test fixture now draws its synthetic flop from undealt cards instead of occasionally duplicating a dealt card. Game rules are unchanged.

The Windows installer was silently installed into an isolated test directory. All 40 installed web files and four desktop-shell files match the build. Public Chrome and installed Windows both decode bidirectional voice and screen sharing through forced TURN/TLS. The public checks cover the sharing popup, Chrome's nine caps with shared sound, Windows' 300/750/1500 kbps caps, live FPS changes, one capture per share, explicit watching, deafen, recipient volume, outgoing gain, private microphone playback, mute/unmute cues, invitations and revisioned permissions. Their two synthetic accounts, one server and media room were removed using the ownership manifest; real counts remain 12 users, three servers and 36 messages. The browser guard stayed below its 4 GiB budget.

The independent pre-release backup verifies all 38 table digests and four file digests, SQLite integrity and foreign keys. Migration 9 was rehearsed on a restored copy, preserving all prior columns; the previous application also starts against the migrated copy. Deployment preserves 35 persistent table digests and all three avatar/attachment files. Runtime configuration is byte-identical, four services are active, and normal-DNS HTTPS serves the exact 0.7.5 HTML. The previous application remains at `/opt/dorham-before-0.7.5`, with its private backup retained. This release does not complete the separately pending domain registration, certify a national Internet outage, add a new media-capacity certification or claim physical acoustic acceptance.
